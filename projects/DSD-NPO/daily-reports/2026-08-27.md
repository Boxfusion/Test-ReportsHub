## 3. Observations and questions for the test lead

1. **Was the public "NPO Database search" descoped?** It has never existed in any build we have tested, across three checks from 13 to 27 August. Thabiso's own note suggests the partner API replaced it. If so, two cases want withdrawing or rewriting rather than standing as failures.
2. **A partner API rated P1 and flagged "critical to test" is not being tested by anyone.** It has no user interface and we hold no API key. It needs either a key or reassignment to development.
3. **Two endpoints are anonymous by design** and the only real question about them is whether they expose personal information. That is a two-minute check, but it is API testing, which the project reserves for development — so it needs an explicit instruction either way.
4. **Should entering "office bearer failed compliance" send the applicant a resubmission email?** The status transition is correct, but no notification is generated, so an organisation whose office bearers all failed is never told to resubmit.
5. **Are administrator account deletions hard or soft?** The relevant case expects a soft delete; that is not observable from the browser, and the answer decides whether the case or the build is wrong.
6. **One organisation status has no records at all** across 104,000+ organisations, which leaves a case permanently unsatisfiable. Should QA manufacture one, or is that state unreachable?

Detailed notes, including the smaller data-quality items, are in `test-reports/observations/2026-08-27-report-notes-and-questions.md`.

## 5. Scope of these claims

Everything above is bound to ADO Functional Test Plan **101543** and to the suites named in section 2; nothing here speaks to the smoke plan, which closed at 70 of 70 on 21 August. Of the 314 cases, **57 carry an explicit blocked or not-executable status with a recorded reason** — chiefly cases needing forced third-party failures, direct API access, or server-side data we cannot reach — and roughly 23 more are duplicates owned by the smoke plan or cases closed in Azure DevOps. The 67.5% is therefore a **floor rather than an estimate**, and the module should not be described as stable on the strength of it: the failure count is high at 93, and the wizard, notification and authorisation areas each carry open defects.
